## 1. Recommendation

Build one user payload, `library/user/reconnaissance/CamHound/` (payload.sh, cam_signatures.txt, README.md), that lists every camera-vendor and camera-capable 802.11 device PineAP Recon can hear, categorised (SECURITY, DOORBELL, BABY, ACTION, DASH, DRONE, BODYCAM, NVR/KIT, MIXED, IOT-MODULE, ENDPOINT, UNKNOWN), graded on a 0-100 confidence scale with four named bands and on-screen reason tags, with proximity shown as a separate bucket so distance orders the list and gates vibration but never removes a row. Passive by default: identity from `_pineap RECON APS/CLIENTS` JSON every 20 s, a room-wide "busy" hint from PineAP's own per-device packet counter delta, and a single-target Watch that measures uplink frame rate and direction from bounded header-only pcaps (CamHound's capture shape, our scoring), with an operator-as-stimulus test for event cameras and a per-run post-Watch verdict card. Locate reuses device_hunter's hot/cold loop with a 5-sample median. A ROOM/SITE mode switch changes alerting, sort and proximity thresholds only. LAN confirmation (RTSP DESCRIBE / ONVIF) exists in the tool but is off by default and hidden until `LAN_CONFIRM=1`, in its own phase (v1.1b). Hardware is assumed available, so the on-device spike is Phase 0 and gates Watch, proximity for clients, the packet-rate hint and the band line. v1 is about 600 LOC of bash plus a 90-line signature file and a 150-line README, resting on the repo-proven primitive set except where Phase 0 explicitly clears a new primitive (header-only pcap capture, hexdump parse, RECON CLIENTS fields).

### 2(b) Ideas adopted or adapted from CamHound

Each entry: verdict, what goes into v2, and the refuter conditions that bind it. "RF" = detection-accuracy refuter, "PF" = platform refuter.

**Watch capture and metrics**

1. Header-only bounded pcap capture parsed by hexdump | awk (from CamHound, IDEA_25, adapted). Replaces v1's long-lived `tcpdump -e -tt -l | awk` text pipeline, which S2 M7 placed outside the safe subset and whose MHz-token parsing killed Design B. Per window of `WIN_SECS=10`: `tcpdump -i wlan1mon -nn -s 32 -w /tmp/cs_up_<A|B>.pcap 'type data and wlan addr2 <target>' 2>/tmp/cs_up.err &` plus the downlink twin (item 2) plus one "others on this BSS" capture `'type data and wlan addr1 <bssid> and not wlan addr2 <target>'`. Windows are double-buffered: window N+1's captures are forked before window N is parsed. Pacing by `timeout $WIN_SECS WAIT_FOR_BUTTON_PRESS A` so A is caught during the capture; then `kill -TERM $pid; wait $pid` per PID (never `timeout -s KILL`, never `killall tcpdump`), so tcpdump flushes its buffer. Parser `pcap_buckets()`: `hexdump -v -e '1/4 "%u\n"' file | awk` skipping the 6-word global header in awk (snaplen from word 5), 16-byte record headers (ts_sec, ts_usec, incl_len, orig_len), payload words skipped by count, all four magics accepted (d4c3b2a1 / 4d3cb2a1 LE, a1b2c3d4 / a1b23c4d BE; the 3c4d variant is ns), truncated trailing record tolerated, abort the window as `parse error` if any incl_len%4 != 0. `greater 1000` moves into awk (`orig_len >= BIG_BYTES`, default 1000) so small frames are counted too. Output per absolute ts_sec: bytes, frames, big frames. `drops N` printed when tcpdump stderr reports kernel drops. Files removed per window; `KEEP_PCAP=1` copies them to loot. RF conditions: double buffering, four magics, SIGTERM, drop count, Phase-0 `od -An -tu4 -j 8 -N 8 file` to confirm incl_len 32, timing of the parser on a 30 s busiest-channel capture, and if < 2 s run the "others" capture at `-s 96` to restore the per-transmitter table. PF conditions: no `-s` to hexdump, parse time must be < WIN_SECS/3 or WIN_SECS grows, lock secs cover window + parse + start latency. Phase 0 items 13a-13e.

2. Kernel-side direction split, two simultaneous BPF captures (from CamHound, IDEA_26, adopted). Uplink = `wlan addr2 <target>`, downlink = `wlan addr1 <target>`, for both client and AP targets (addr2 is the transmitter in ToDS and FromDS frames alike; the "swap for AP" clause in CH is wrong, see IDEA_27 below). `asym = U_bytes / (D_bytes + 1)` on bytes, evaluated only when U_frames >= 50 in the window, printed `-` otherwise; `dn` printed `-` when D_frames == 0. Both files bucketed on absolute ts_sec. Behaviour axis rows: asym >= THR_ASYM over >= 2 windows +15; down-heavy = asym <= THR_DOWN (2.5, config, stored x10) over >= 2 windows with D_frames > 0: -20, tag `down-heavy` (the one rule that also names the DOWN verdict word; there is no separate "asym < 1" test). asym never promotes to CONFIRMED alone. Phase 0 item 14 repeated with both captures on the busiest channel.

3. Operator-as-stimulus baseline/stimulus/post protocol (from CamHound, IDEA_21, adopted with PF corrections). Watch becomes a sub-menu: `Live view` and `Stimulus test (~90 s)`. Sequence: quiet gate (wait until < 2 big uplink fr/s for 15 s, cap 60 s, text "waiting for camera to settle"), PROMPT "Baseline 30s. Keep still." (blocking, A starts), then and only then `PINEAPPLE_EXAMINE_BSSID <bssid> $((WIN_BASE_S+10))`, capture baseline, VIBRATE 100, ALERT "Now move 20s: walk, wave, lights", re-lock `$((WIN_STIM_S+10))`, capture stimulus, LOG "settling 20s", re-lock, capture post (WIN_POST_S=20, always on), verdict. Lock is issued after each blocking dialog returns and re-issued before every window, so a long dialog cannot expire it (CH p38 and v1 of this idea both had the lock-then-PROMPT ordering bug). `wait $P_UP $P_DOWN` by PID, never a bare `wait` (the watchdog subshell is a child and a bare wait would hang the payload with the lock held). Targets with no ap_bssid cannot be stimulus-tested (item 12). Metrics in big frames per direction, not bytes: U_base, U_stim, U_post, D_*; `delta = max(U_stim, U_post) / max(U_base, THR_DELTA_FLOOR=2)`. EVENT if delta >= THR_DELTA (2.0) AND max(U_stim,U_post) >= THR_STIM_UP (8 big fr/s) AND asym >= THR_ASYM (3): behaviour +60 tag EVENT; weak (delta >= 1.5) +40 tag EVENT?. Null-result text: "no change: asleep, disarmed, in cooldown, local-record, or not a camera; identity only". EVENT on a VENDOR_ENDPOINT or randomized-MAC row caps at LIKELY with text "responds to motion: webcam or camera; vendor <X>". The test may be launched from an AP row (per-SA uplink deltas so a dormant Blink that wakes appears as a new SA). RF conditions: the cooldown hint on the repeat card (Blink 30-60 s, Ring Standard dwell, Wyze free tier 5 min), the `less 400` small-frame count for IDLE vs NONE. Phase 0 addendum: Blink/Ring-class camera baseline vs wave, Wyze/Tapo idle vs live view, CPU with three tcpdump instances.

4. Post-stimulus recovery window (from CamHound, IDEA_22, adapted). WIN_POST_S=20 is always captured and feeds delta via max(U_stim, U_post), because store-and-forward cameras upload after the clip. `rec = U_post / max(U_stim,1)` is logged in the watch tsv and shown as `post x.x`, not scored in v1. v2 may use rec as a class label (real-time vs store-and-forward), never as a confidence modifier. WIN_POST_S is a config key so an operator on low battery can shorten it.

5. Repeat-and-combine verdicts (from CamHound, IDEA_23, adopted). The verdict card is the same LIST_PICKER as the Live-view summary (item 11): `Repeat (n/MAX_RUNS)` (shown for stimulus runs only), `Locate`, `Watch again`, `Back`; no directional binding, because `timeout N WAIT_FOR_INPUT` is unproven (spike 16) and item 25 keeps UP/DOWN/LEFT/RIGHT inert. Repeat re-issues the lock and runs baseline/stim/post again; `RUNS[]` keeps each run's metrics; the card shows "best of N runs" using the best delta and that run's asym/cv/rates; every run appended to `watch_<ts>_<mactail>.tsv` with `-` placeholders. MAX_RUNS=3 per target per session; after the cap the card says "max runs; move closer or try Live view". "Repeat later" keeps RUNS[] for the MAC within the session. Cannot be gamed: an idle device cannot produce 8 big uplink fr/s by chance.

6. Multi-metric verdict with stated thresholds (from CamHound, IDEA_24, adapted to frame counts). Computed in one awk pass as fixed-point integers x10: up (mean big uplink fr/s), down, asym (bytes), cv (stdev/mean of per-second uplink big-frame counts, first and last partial buckets discarded, needs >= 6 full buckets, guarded for n < 2), delta, rec. Config: THR_STREAM_UP=10, THR_ASYM=3, THR_CV=0.6, THR_DELTA=2.0, THR_DELTA_WEAK=1.5, THR_STIM_UP=8; THR_FSIZE and THR_PERIOD reserved for v2. Verdict card line 1 `EVENT  best of 2` / `STREAM` / `DOWN` / `IDLE` / `NONE`; line 2 `up 14/s as 9 cv .4`; line 3 `delta 3.2 post 0.9`. Same fields in order `verdict up down asym cv delta rec runs` in the watch tsv and in inventory `signals`. Uplink is defined as addr2 == target everywhere, including Live view. README "what it cannot see" lists sub-300 kbps streams (frame counts under-count sub-1000-byte video) and UL-OFDMA Wi-Fi 6 uplinks; v1 ignores the Retry flag.

7. Behaviour classes named in the verdict (from CamHound, IDEA_20, adapted). STREAM = uplink big fr/s >= THR_STREAM_UP over >= 4 windows AND asym >= THR_ASYM AND cv <= THR_CV: behaviour +55 (rate 25/30 + sustained 10 + asym 15), red only when identity >= 45. EVENT = item 3. DOWN = asym <= THR_DOWN (2.5) over >= 2 windows with D_frames > 0: behaviour -20 (identical to the `down-heavy` row in 5.3; the word and the score use one threshold), text "two-way or download: call, phone, update; not camera-like". IDLE = small frames present (the `less 400` count) and big < 2/s in every window and delta < 1.2: behaviour 0, text "idle: asleep, disarmed, local-record, or not a camera; low-rate streams can read as idle; identity only". NONE/INCONCLUSIVE = item 8. The 22-char abbreviations STREAM/EVENT/DOWN/IDLE/NONE are the LOG words. README carries the three-class table (cloud-streaming / event-upload / local-record) with "how CamHound tests it" and "what it cannot see" per class. Keepalive periodicity (`period`) stays v2 pending lab data.

8. INCONCLUSIVE as a grade, structural definition (from CamHound, IDEA_31, adapted). INCONCLUSIVE when U_frames == 0 over the first two windows (not a 20-frame floor); sub-text by D_frames: 0 -> "nothing heard on this channel: lock, band or sleep"; > 0 -> "AP heard, target silent: asleep, or too far for its data frames; move closer". The screen prints Recon's last RSSI for the target ("likely too far" below -72 dBm), the lock read-back line from `iwinfo wlan1mon info` (e.g. `wlan1mon ch 6, target ch 6` or `ch 1 != 36, lock failed`, or "wlan1mon did not follow to 5 GHz"), and the RECON last-seen age. LED YELLOW, VIBRATE 100 once. A = keep watching, B = back; no `exec "$0"` (bypasses the EXIT trap and orphans the lock). Identity grade stays on the same screen. `INCONCLUSIVE_FRAMES=20` remains a config key as a display hint only. README: "INCONCLUSIVE is about the measurement, not the device."

9. Always lock by EXAMINE_BSSID, both roles (from CamHound, IDEA_33, adopted). `PINEAPPLE_EXAMINE_BSSID <bssid> <secs>` for client hits (its ap_mac) and AP hits (its own mac); v1's EXAMINE_CHANNEL branch is deleted. Lock-verify: read `iwinfo wlan1mon info | grep Channel` three times over ~1.5 s; locked iff all three equal the target's Recon channel; if equal to each other but not the target, fall back once to `PINEAPPLE_EXAMINE_CHANNEL <ch> <secs>` and re-verify ("locked by channel"); if they differ from each other the radio is still hopping and Watch reports "lock failed" instead of INCONCLUSIVE. secs = WIN_SECS*2+5 re-asserted per window only after Phase 0 item 8 shows a 10x re-lock keeps Recon alive; otherwise lock once per Watch with secs = total window length. Channel/freq from RECON JSON are display-only. Phase 0 item 8 extended with a 5 GHz VHT80 AP and a `width:`/`center1:` read-back; if PineAP parks at 20 MHz, Watch reads the target AP's operating width from one beacon capture and prints "5 GHz 40/80 MHz uplink not decodable on wlan1mon" instead of "idle".

10. Retry-aware counting deferred with a corrected mechanism (from CamHound, IDEA_28, adapted into v2). v1: a retry percentage note via a BPF count (`wlan[1] & 0x08 != 0`) only if Phase 0 shows the `wlan[]` accessor compiles for the radiotap DLT on this libpcap; otherwise nothing. v2: dedupe by (TID, seq) per direction file at `-s 128` (SNAPLEN config), it_len read per record, fragments and management excluded, capped records per window, only if parse time < WIN_SECS/3. Dropping every Retry frame (CH's version) under-counts because the sniffer often hears only the retry.

11. Post-Watch summary screen with next actions (from CamHound, IDEA_43, adapted). After the loop ends: two LOG calls (coloured verdict line; white 3-line metric block). Rate shown as a band (`<0.5 / 0.5-2 / 2-8 / >8 Mbps`), never a decimal. "(weak)" appended to any non-STREAM verdict when the target's last Recon RSSI is below WATCH_MIN_RSSI (-72 dBm, the same key that drives the Watch header warning). Then one LIST_PICKER shared with the stimulus verdict card: `Repeat (n/MAX_RUNS)` (stimulus runs only), `Locate`, `Watch again`, `Back`; Watch again re-enters the same function (no exec), capped at 5 consecutive repeats so the EXAMINE total stays bounded; `secs` re-passed on every re-lock. One shared `upsert_inventory()` used by scan and Watch; beh_score and beh_verdict are a monotonic max over Watches with the timestamp of the max; watch_<ts>.tsv keeps every episode. For AP-mode targets the idle word is QUIET.

12. No stimulus/Watch on unassociated clients (from CamHound, IDEA_35, adapted). ap_mac of "", "-", absent, 00:00:00:00:00:00 or ff:ff:ff:ff:ff:ff = unassociated. Detail card replaces the Watch row with `Watch n/a (not associated)` and text "probe-only: identity + Locate; Locate updates only on probe bursts (15-60 s) and the MAC may rotate"; a locally-administered probe-only MAC gets no Locate offer. Never ERROR_DIALOG + exit 1. inventory ap_bssid uses `-`. In the v1.1 hook test `_RECON_SELECTED_CLIENT_BSSID` then `_RECON_SELECTED_AP_BSSID`. Phase 0 items 3 and 9 record how probe-only clients appear and what MONITOR prints for one.

13. AP-mode direction correctness and the NVR-kit signal (from CamHound, IDEA_27 and IDEA_13, adapted; contested, see 2(c)). The direction part is correct and in v1 (item 2). The KIT identity signal is re-specified on resolved vendor labels, not raw 3-byte prefixes (Arlo has three blocks, Wyze six, Hikvision 86; a raw-prefix test misses the kits it names). KIT fires when >= KIT_MIN_CLIENTS (1) associated clients ALL resolve to the same pure-camera VENDOR label AND the AP resolves to that label (or the AP is hidden/LAA with no vendor hit): AP +35 tag KIT-AP, counts as an independent identity class; clients inherit the verdict silently with tag KIT-CL (no LED/vibe/dialog of their own); one alert per kit on the AP row: "<Brand> camera kit, N cams". When the consensus label is MODULE and the AP is hidden or has a non-dictionary SSID: tag KIT? +10 (POSSIBLE) so white-label Zosi/Hiseeu-class kits surface in the modules list. TP-Link AP with TP-Link clients: KIT? +10 only (Deco/eero shape). Implementation: AP->client map built per JSON object (`jq '.[] | [.mac, (.ap_mac // "-")] | join("|")'`; in grep -o fallback mode the KIT signal is disabled), MACs case-folded, probe-only rows skipped, zero forks. Stub cases: Arlo base A4:11:62 with two FC:9C:98 cameras = CONFIRMED kit, one alert; Reolink EC:71:DB NVR with two EC:71:DB cams = CONFIRMED, one alert; hidden 02:xx AP with three Realtek clients = KIT? POSSIBLE; TP-Link AP with three TP-Link clients = KIT? POSSIBLE.

15. Proximity as a separate bucket (from CamHound, IDEA_12, adapted: no multiplicative gate). Bucket from the best RSSI over the last 3 cycles: NEAR >= NEAR_DBM, MID, FAR < FAR_DBM, UNK when no reading or when the record's last-seen is older than 90 s. Mode defaults ROOM -60/-75, SITE -70/-85; thresholds shifted 7 dB lower for 5 GHz records and a further 6 dB for client records (RF condition), replaced by Phase 0b calibration at three distances per band; until calibrated the status line says `prox: uncal`. Source: AP records use the max of beacon[].signal and response[].signal (device_hunter:122 proves the key); client records use the CLIENTS JSON signal key only if Phase 0 item 3 shows it (or the text form of `_pineap RECON CLIENTS` if only that has it); never inherit the AP's RSSI for a client; UNK fails open (never suppresses a vibe). Loot gains `prox`, `rssi_last`, `rssi_best_ts`. Status line shows `cRSSI n/a` when the client key is absent. Re-alert rule "RSSI improved >= 10 dB" now reads as "moved into MID".

16. Probed-SSID term demoted to a tag (from CamHound, IDEA_14, adapted; reverses v1's S6 cut only as a +5 tag). PROBE: a client's probed SSID matching an SSID or SSID_WEAK row -> +5, tag PROBE, tie-breaker only, never crosses a gate, ignored for randomized MACs. Read from the CLIENTS JSON only (`.probes // .probed_ssids // []` with jq; no grep -o fallback); if Phase 0 item 3 shows no probe key the row ships commented with the spike result noted and PROBE exists only in the v1.1 hook via `_RECON_SELECTED_CLIENT_PROBED_SSID` (singular; the plural is a count). Optional v1.1: PROBE-HIDDEN +10 when a camera-class or MODULE client's probed SSID matches no beaconed SSID but a hidden AP of the same vendor exists.

17. Packet-rate proxy for room-wide activity (from CamHound, IDEA_15, adapted: delta between polls, not top decile). Parse `.packets // 0` from APS and CLIENTS; keep PREV_PKT[mac], PREV_T[mac]; RATE[mac] = (pkt - prev)/(now - prev_t) x10 fixed point, only when prev exists and the delta >= 0 (negative = Recon restarted: reset, no rate); clear PREV_* on return from any EXAMINE/MONITOR lock or when now - prev_t > 2x CYCLE_SECS. Client rows only. One definition, used verbatim in 5.3 and 6.3: BUSY = RATE >= BUSY_PPS (10 counted frames/s as PineAP counts them; calibrated in Phase 0b) for BUSY_CYCLES (2) consecutive cycles AND rank in the top 3 by RATE among clients on the same band: behaviour +10, tag BUSY. The cycle is the unit (Phase 0 item 30 confirms that CYCLE_SECS=20 spans >= 2 PineAP hop periods; there is no separate frames-per-cycle floor). inventory.tsv gains `pkt_rate` (RATE x10) after `n_seen`. Effects: sort keys, row suffix `busy`, status `B<N>`, the one-time LOG hint. Parse k/M suffixes in the hook path (`_RECON_SELECTED_CLIENT_PACKETS` is human-readable). README states the counter is direction-blind and band-biased. Gated on Phase 0 item 3 showing `packets` in a CLIENTS object; APS `packets` is proven (find_hackers:65). ## 5. Confidence model

All weights and thresholds below are lab starting points (Skeptic 1 defaults); the README test matrix carries a Measured column filled from Phase 0b and Phase 3b.

### 5.1 Two axes, one displayed number

Identity axis I (0-100, clamped) = sum of the identity rows below for the device. Behaviour axis Bh (clamped -20..100) = sum of the behaviour rows (Watch, stimulus, BUSY). Both are stored; the screen shows one number:

conf = clamp(0, 100, I_eff + Bh_eff), where
- I_eff = I, except that if only ONE identity class fired (see 5.4) then I_eff = min(I, 69).
- Bh_eff = Bh when I >= 12. When I < 12 (no identity): if EVENT or EVENT? fired on a globally administered, non-ENDPOINT MAC, Bh_eff = Bh (the operator timed the stimulus); otherwise Bh_eff = min(Bh, 69) and the row sits in the STREAM lane.
- Bh_eff = max(Bh_eff, 0) whenever I >= 45: a negative behaviour row (down-heavy) never lowers a grade that identity alone earns; for I < 45 it lowers conf and sets the verdict word.
- Gate caps, applied after the sum: if none of the 5.4 CONFIRMED paths holds (two classes summing >= 80; one class >= 45 with gate-behaviour >= 25; FEED), conf = min(conf, 79). If none of the LIKELY paths holds (I >= 45; Bh >= 55 with I >= 12; EVENT or EVENT? on a global non-ENDPOINT MAC; Bh >= 70 on a global non-ENDPOINT MAC), conf = min(conf, 44).
- A randomized (locally administered) client MAC caps conf at 69 (never CONFIRMED) in addition to its -40.
- A VENDOR_ENDPOINT row caps conf at 79 unless FEED or EVENT fired (a laptop that passes the stimulus test is a webcam; still never red).
- A device with I <= 0 and Bh <= 0 has conf 0 (not listed on screen; present in the report under ENDPOINT/UNKNOWN).

Bands (named, continuous underneath):

| Band | conf | Colour | Meaning on the card |
|---|---|---|---|
| CONFIRMED | 80-100 | red | two independent identity classes, or camera-brand identity plus streaming/stimulus behaviour, or a LAN feed |
| LIKELY | 45-79 | amber | camera-brand hardware (one class) or a mixed vendor that is streaming, or a device that responded to the stimulus |
| POSSIBLE | 20-44 | white | one weak signal (mixed vendor, camera word, module with a co-hit); list only |
| STREAM lane | 20-69 with I < 12 | yellow | streaming-consistent behaviour with no identity (webinar laptop or a module cam being live-viewed); operator decides |
| MODULE | 0 with tag MODULE | white, own list | unidentified IoT module; "check these" |
| none | < 20 | not shown | report only |

Mixed-vendor client (+20) + EVENT 60 + asym 15 + BUSY 10 = 105 -> no CONFIRMED path (one class below 45) -> 79 LIKELY. Idle Blink on an Amazon Technologies OUI = 20 POSSIBLE, listed, category MIXED, no vibe. Espressif client alone = 0, modules list. Espressif client on an AP beaconing IPC_1234 = 15 (SSID_WEAK), listed under the modules divider with the SSID tag, no vibe. Espressif client + Watch STREAM = 55 STREAM lane (yellow). Espressif client + EVENT 60 + asym 15 = 75 LIKELY ("responds to motion: likely camera"). ### 5.3 Behaviour axis rows (Watch and scan)

| Row / tag | Points | Source |
|---|---|---|

### 5.4 Independent classes and the CONFIRMED gate

Identity classes: OUI (OUI, VENDOR, VENDOR_WEAK rows), SSID (SSID, SSID_WEAK rows), WPS, KIT, LAN. Fixed tags (HIDDEN, RAND, PROBE, KIT?, MODULE, BUSY and all behaviour tags) are never a class. CONFIRMED (conf >= 80) is reachable only by: two different classes whose rows sum to >= 80; or one class >= 45 plus gate-behaviour >= 25, where gate-behaviour counts only the STREAM, EVENT, EVENT? and asym rows (BUSY is excluded so that asym 15 + BUSY 10 cannot reach the gate); or FEED plus any OUI/SSID hit. The two-tag display rule: tags are ordered so the two gate classes come first.

### 5.5 Proximity (separate from both axes)

Bucket per record from the best RSSI of the last 3 cycles: NEAR >= NEAR_DBM, MID, FAR < FAR_DBM, UNK (no reading, or last-seen > 90 s, or client record without a client signal key). Defaults: ROOM NEAR_DBM=-60 FAR_DBM=-75; SITE -70/-85; for 5 GHz records both thresholds minus 7 dB; for client records a further minus 6 dB; Phase 0b replaces these with three-distance calibration per band. Effects: sort within a band; which NEW LIKELY/CONFIRMED rows vibrate (ALERT_FAR); the re-alert rule ("moved into MID"); the `?` char on rows with UNK never suppresses anything.
