# Bench 2026-11-19: does the Disrupt rung fire, and what does BOTH add

Written before the bench, from master `e245207`; every line here is a prediction to be checked,
not a result. The only Disrupt ever looted from the user payload (CLAUDE.md "Second contact",
2026-11-05) fired `PINEAPPLE_DEAUTH_CLIENT_ALL`, which "Third contact" showed sends opcode 402 and
builds no deauth frame. Since `82fa566` (the transmit-set fix) and round 2 (`csa_issue` rc 3, the
read-down, the lock text) CLAUDE.md records **no device run of the rung at all**, so arm A is the
first time the opcode-400 frame leaves the radio from CamHound rather than from a hand-typed command.

Commands are quote-free where they can be (the PowerShell paste rule). Read `events.log` with
`grep -e .resp. -e .assoc. /root/loot/CamHound/events.log` — repeated `-e` rather than
`grep -E ' (resp|assoc) '`, because the parens and the `|` need quoting twice over, once for
PowerShell and once so `ash` does not read the `|` as a pipe (dev/CamHound/README.md's rule, four
measured incidents). Checked against the code by two sceptics on 2026-11-19; their corrections are
folded in below.

## 1. The oracle question this bench can settle

`resp_verdict` scores each subject from Recon's packet counter and last-seen stamp, read before the
fire (`pk_before`) and `RESP_SETTLE_SECS` = 6 s after it (`pk_after`), in this order: no numeric
baseline → `INCONCLUSIVE`; subject gone from the Recon list → `MOVED`; no numeric post-read →
`INCONCLUSIVE`; counter advanced → `NO_EFFECT`; counter unchanged and last-seen unchanged → `MOVED`;
otherwise `INCONCLUSIVE`. "Whether Recon's packet counters move the way `resp_verdict` assumes" is
the first item in CLAUDE.md's open list. For every arm write down the feed's behaviour with clock
times beside the loot verdict:

| the feed / phone | verdict | reads as |
|---|---|---|
| dropped, stayed down past the 6 s | `MOVED` | the oracle agrees |
| dropped, back within ~6 s | `NO_EFFECT` | the settle window is shorter than the re-association, and the return traffic is what the counter counted — the window, not the frame, is the defect |
| nothing visible | `NO_EFFECT` | agree |
| nothing visible | `MOVED` | the weak producer CLAUDE.md names: a stalled counter on a quiet device |
| anything | `INCONCLUSIVE` | look at `pk_before` and `pk_after`: a `-` means the subject was heard but never measurable (randomised MAC, or no Recon row) |

`lock=unverified` in the loot is **not** a failure (rc 3 proceeds); `INCONCLUSIVE by construction`
in the log is the zero-member AP-row fire, also not a failure.

**F. The sustained-CSA probe, by hand** — the empirical half of "keep firing until it moves".
Fourth contact's constant-freeze arm (mode 1, announce ch 1, count 3) ran 10 s; this runs it for 60:
```sh
# the interface FIRST, then the park -- run_17a.sh sequences it this way on purpose, because
# Fourth contact measured wlan1mon administratively DOWN (flags 0x1102, no IFF_UP) while pineapd
# ran: that run issued the lock and transmitted NOTHING (rc=1, no beacon captured) and the feed did
# not freeze. Do not read a null arm as a client observation.
cat /sys/class/net/wlan1mon/flags
ip link set wlan1mon up
PINEAPPLE_EXAMINE_BSSID FC:58:5A:08:42:15 120
PINEAPPLE_EXAMINE_CHANNEL 8 120
iw dev wlan1mon info | grep channel
iw dev wlan1mon info | grep channel
/root/pagerinj -i wlan1mon --csa --bssid FC:58:5A:08:42:15 --chan 1 --count 3 --mode 1 --secs 60 --wait 10
iw dev wlan1mon info | grep channel
PINEAPPLE_EXAMINE_RESET
```
The `flags` value must have its `0x1` bit set (`0x1103`, not `0x1102`). Both channel reads before
pagerinj must say 8. The read **after** pagerinj is the one that says the lock held for the whole
60 s: nothing in this repo has asked EXAMINE for more than 30 s (`run_17a.sh` hard-codes 30) and no
cap is documented, so a lock that quietly expired would let pineapd hop mid-flood and read exactly
like the client breaking through. Run `PINEAPPLE_EXAMINE_RESET` even if pagerinj exits non-zero.
`--mode 1` is pagerinj's default and `--rate` is left at its default 10 frames/s on purpose: that is
the ~1:1 alternation with the AP's 9.68 beacons/s that Eighth contact measured, so changing it breaks
comparability with every arm above. `run_17a.sh` cannot host this arm: it hard-codes `--secs 10`.
Watch three things with clock times: does the feed
stay frozen for the whole 60 s or does it break through (Sixth contact's intermittent pattern);
does it recover when the flood stops; does the camera ever leave ch 8 (Recon list, or
`_pineap RECON DEVICES`). Keep pagerinj's `sent=… failed=…` line. Then, if the feed held, the same
with `--mode 0`: Seventh contact's re-association churn, which is the other candidate for a
sustained mode.

## 4. On "fire until the target has moved" — the design answer, pending F

Worth building, but not with that stop condition, for four reasons read from the code and the bench:

1. **`MOVED` is the weak word, and it fires on success.** Its two producers (`resp_verdict`) are the
   subject dropping out of Recon, and its packet counter plus last-seen stamp both standing still —
   and a mode-1 quiesce IS a standing-still counter, because Recon counts frames heard from the
   subject and a quiesced client sends none. So a loop that stops on `MOVED` stops exactly when the
   denial is working, with the target still associated, and stops spuriously on an idle camera that
   was never affected. The one measured mode-1 quiesce was partial (Seventh contact: `6, 83, 93,
   263 … 12 …` client→AP frames/s, a trough of 12, never zero), so over `RESP_SETTLE_SECS` = 6 s that
   counter would have advanced and read `NO_EFFECT` — the loop would have run forever on the one
   client we have numbers for. Either way the word is not a stop condition. And `resp_aggregate`
   returns `NO_EFFECT` if ANY subject kept transmitting, so on a BSS-wide attack the attempt's word
   and the picked target's (`tgt_verdict`) disagree, and `tgt_verdict` is `-` for a randomised MAC —
   which is the only station on this BSS. A sustained mode should stop on the operator, on a clamped
   total, and on the injector refusing; never on a verdict.
2. **The measured effect of a CSA on this client is denial WHILE transmitting, never a move.**
   Mode 1 froze the feed for the length of the run and the client recovered when injection stopped
   (Fourth contact); mode 0 made it leave and rejoin ch 8 three times in 11 s with zero deauth or
   disassoc (Seventh and Eighth contact); no capture shows the station changing channel. So the
   capability on offer is a sustained window, and "until moved" would wait for an event nobody has
   observed.
3. **The firmware CSA must never loop.** `PINEAPPLE_DEAUTH_CLIENT_CSA` announces channel 14 with
   count 0 — nothing a US client can act on — and each call freezes pineapd's hop for 5 s. A
   sustained mode is injector-only, and `posture_expect` already labels the firmware leg `fw-broken`.
4. **The shape already exists in the payload.** `locate_target` runs a background process and polls
   `WAIT_FOR_BUTTON_PRESS A` with a 1 s timeout until A stops it; `csa_clamp` bounds a window to
   1–60 s because `pagerinj --secs 0` means "until signalled" and the EXAMINE lock has a budget. A
   sustained mode would be **one `pagerinj` run held open, not a train of short ones**. Each
   invocation re-captures a beacon to clone before it transmits (`capture_beacon`, `pagerinj.c:1458`;
   `return 1` with no summary on failure, `:1468`), so a window costs up to `CSA_INJ_WAIT` before a
   frame leaves, and `csa_issue` adds ~1.5 s of `lock_target` read-backs and `resp_fire` a 6 s
   `RESP_SETTLE_SECS` sleep: at the shipped 3 s/5 s that is 3 s on the air per ~16 s window, under a
   20% duty cycle, and in every gap the AP's own beacons (9.68/s, no gap over 250 ms, Eighth contact)
   abort the pending switch (`mlme.c:2452`) and release the queues. Windows would reproduce Sixth
   contact's *intermittent* arms, not Fourth contact's constant freeze. So: one invocation with
   `--secs` set to the clamped total, stopped with SIGTERM — which `pagerinj` catches (`:1531-1532`),
   breaking its loop and printing the summary with its `interrupted: ` prefix, which `csa_issue`
   already reads as rc 2 — with the counters read once before and once after, not per window. The
   stops, with what each costs: **A pressed** is reachable only while the injector is NOT being
   `wait`ed on, so the poll loop must own the child rather than `csa_issue`'s blocking `wait`; **a
   clamped maximum total**, which `csa_clamp`'s 1–60 already bounds and the EXAMINE lock must cover;
   **the injector refusing**, which is `csa_issue` rc 1 (`sent=0`, pagerinj's own `failed && !sent`)
   and not a stderr scrape — pagerinj prints one `sent=/failed=` summary (`:1604`) and no per-frame
   report, and the measured flaps were `sent=93 failed=5` and `sent=84 failed=7`, which a "failed on
   every frame" test would have missed entirely. Not "subject absent from Recon for K windows": that
   is `present=0`, the weak producer again, and under a long park Recon stops hearing everything off
   the locked channel anyway. It must refuse to start when `ui_ok` is false: `locate_target`'s `else
   sleep 1` branch polls no button, which for a transmitter means no stop at all. The loot stays one
   `responses.tsv` row per subject — `RESP_HDR` is fixed at 16 columns and §0 item 6 pins it for the
   operator, so no new columns; a held run's duration is the gap between its `fire` and `verdict`
   lines in `events.log`. And the key must be gated where it is OFFERED, not only labelled:
   `posture_opts` returns the literal `DEAUTH BOTH CSA` with no injector test (that test is in
   `posture_expect`), so a sustained key added there would be offered with `CSA_INJECTOR` empty and
   fall through to the firmware command, the one thing reason 3 forbids; gate it on
   `[ -n "$CSA_INJECTOR" ] && [ -x "$CSA_INJECTOR" ]` in `posture_opts`.

Decide after F, and note which arm F is: mode 1 with announce ch 1 against a BSS on ch 8 is **Fourth
contact's constant-freeze arm** (`CSA {37,3,mode=1,ch=1,count=3}`, `sent=97 failed=0`), run for 60 s
instead of 10. Sixth contact's two *intermittent* arms each differ from it by one variable — mode 1
with announce = current, and mode 0 — so neither is what F repeats. Four outcomes, not two:

- **Holds all 60 s and the feed returns when the flood stops** — the sustained mode has a measured
  mechanism. Build it as ONE held `pagerinj` run (reason 4), not as windows.
- **Holds, and the feed does NOT return** — the client was lost rather than quiesced, which six
  mode-1 arms with zero auth/assoc (Seventh contact) do not predict. Stop and capture on the parked
  primary before building anything.
- **Breaks through after more than ~10 s** — the freeze has a lifetime between 10 and 60 s. That is
  a finding about duration, and it still argues for one long window; it does not say the stimulus is
  wrong.
- **Breaks through inside the first ~10 s** — it contradicts Fourth contact at its own duration, so
  the stimulus is what needs work first, not the loop.

Before reading any of them, check pagerinj's `failed=`: two of Sixth contact's three arms came back
`failed=5` and `failed=7` with `!! PARTIAL RUN`, and 60 s is six times the exposure. A run whose
`failed=` is a large fraction of `sent=` decides nothing.
