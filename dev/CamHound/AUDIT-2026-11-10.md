# Audit of the CSA injector hook, the transmit-gate fix and the bench runner

Run 2026-11-10 against `cce6e13`. 122 agents, 0 errors, 8 finder dimensions, 38 raw findings,
3 verification lenses per finding (trace / intent / impact).

**The workflow's own tally — "15 of 38 refuted, 23 survive, 0 unverified" — is not trustworthy and
is not reproduced here.** The run was a *resume*, so agent results replay from cache when
`(prompt, opts)` is unchanged. That cached both the finders AND the verifiers, because a verifier's
prompt is derived from its finding's text and neither changed. So a majority of the surviving
findings were raised against, and "confirmed" against, the code as it stood BEFORE `cce6e13` and
`a63c0ef`. One verifier reported reproducing `CSA bss (fw-broken)` from a live harness run; the
harness at this commit prints `CSA bss (injector)`, which is what a cached pre-fix verifier would
say. **Every claim below was therefore re-verified by hand against the tip**, and the tally restated
from that. This is the second time this audit's bookkeeping has produced a number that looked like
evidence and was not; the first was counting a dead verifier as a refutation.

## Open question, not a defect — the operator's call

`CLI_AWK` admits a station only when `seen[c] >= 2` (`payload.sh`, `CLI_AWK`'s final `for` loop).
That threshold is deliberate and documented in place: a monitor interface delivers FCS-corrupt
frames, so a single sighting can be a corrupt address. The consequence is that a BSS proven occupied
by hundreds of records can admit zero members, and an AP row then refuses with `NO_CLIENTS` —
declining to transmit a **broadcast** frame that needs no member list at all.

That is the same root cause as the transmit gate fixed on 2026-11-09 (`82fa566`): a gate that exists
to keep the *oracle* honest suppressing the *frame*. The difference, and why it is not being changed
unilaterally: that fix admitted stations the capture had *heard*, where this would transmit with
**no** member list recovered, which widens blast radius on a path where CamHound currently stays
silent. The confirm already names the breadth ("on EVERY client of <bssid>").

*Falsified by:* an AP row whose capture shows `recs > 0` and `n=0` where a GUI AP-row deauth, fired
at the same BSSID seconds later, disconnects a client — that would show the refusal is costing a
working attack, not preventing a blind one.

## Found on the bench the same day, in code this audit had just passed: `iface_up` read the wrong file first

The operator ran the count-0 control arm and it refused to fire:

```
-- target FC:58:5A:08:42:15 ch 8 (2447 MHz); announcing ch 1 with count 0 on wlan1mon
-- parking with EXAMINE for 30s (pineapd left running: it owns wlan1mon)
wlan1mon is not up, so nothing can be transmitted.
```

**The reading, `[V]`:** `iface_up` tested `/sys/class/net/<if>/operstate` first against an
`up|unknown` whitelist and returned 1 (down) for anything else, only reaching the `flags` test if
operstate already said yes.

**The inference, which is the attackable part:** `operstate` is an RFC2863 *carrier* notion
(`net/core/link_watch.c`, `rfc2863_policy`), so a netdev that never calls `netif_carrier_on` reads
`down` there regardless of its administrative state. A mac80211 monitor vif is such a device.
`flags` bit 0 **is** `IFF_UP`, the administrative state, which is the thing the script wants to
know. So the two files were consulted in the wrong order and the authoritative one was gated behind
the advisory one.

**Fixed** by making `flags` primary, `operstate` the fallback for a kernel that does not export
flags, and the function three-state: 0 up, 1 positively down, **2 the kernel did not say**. Callers
now use `iface_down`, which is true only for 1, because the old `|| ` form read "no answer" as bad
news — `absent` returned 1 under the old function, a positive claim of down about an interface that
does not exist.

**Mutation test**, the shipped function text extracted by line range and run against a fixture
`NET_SYS` tree. New: 14 pass, 0 fail. Old, same fixtures: 6 fail, and the one that matters is
`flags=0x1003 operstate=down` → old 1, new 0. That is the bench case.

**And the gate itself was wrong in kind, not just in detail.** It called `die()`. A heuristic sysfs
read was given a veto over a measurement that has its own ground truth — `pagerinj`'s rc, which the
`==` banner already reports unambiguously — so a wrong reading did not degrade the run, it
cancelled it. It now warns, tries `bring_up`, and fires anyway. *Falsified by:* a run where the
banner says `FRAMES LEFT THE RADIO` and no frame reached an external receiver.

**Why no pass caught it.** Every audit lens read this function as shell and it is correct shell;
the defect is a claim about what Linux writes in two sysfs files, and nothing in the repo exercised
it against either a device or a fixture. The fixture tree above now exists, so the next change to
it is cheap to attack. This is the third instance in two days of *correct reading, wrong inference*
— and the second where the wrong inference was mine.

### ⚠ REFUTED THE SAME DAY, ON THE BENCH, BY THE DIAGNOSTIC I ASKED FOR: the cause above is wrong

The section immediately above says the bench refusal happened because `operstate` reads `down` on a
mac80211 monitor vif whose `IFF_UP` is set. **That combination does not occur on this device.**

Measured, two runs of `run_17a.sh` minutes apart, reading both files before the run:

| run | `flags` | `operstate` | `IFF_UP` (bit 0) | old `iface_up` would say | truth |
|---|---|---|---|---|---|
| 1 | `0x1102` | `down` | **clear** | down | **down** — correct |
| 2 | `0x1103` | `unknown` | set | up | up — correct |

So when `IFF_UP` is set this device reports `operstate` **`unknown`**, which the old `up|unknown`
whitelist *accepted*; and when `operstate` says `down`, `flags` agrees. **The old function would
have answered correctly on both readings.** The fixture case the fix was built around,
`flags=0x1003 operstate=down`, is synthetic — I wrote it to match my hypothesis and it passed
because the hypothesis was baked into the fixture.

**What actually happened on the bench:** `wlan1mon` was genuinely administratively down
(`0x1102` — `IFF_BROADCAST|IFF_PROMISC|IFF_MULTICAST`, no `IFF_UP`), with pineapd running (pid
11482). The old gate identified that correctly and refused. Its real and only defect was `die()`:
it gave up instead of trying `bring_up` and reporting honestly. Run 1 under the new code did try,
printed `NOTHING WAS TRANSMITTED (pagerinj rc=1)`, and the very next run came up `0x1103` and fired.

**What survives of the change.** The `die()` → warn + `bring_up` + fire demotion is what unblocked
the bench, and it is vindicated. The `absent` → rc 2 fix is a genuine correctness improvement: a
nonexistent interface must not yield a positive claim of "down". Making `flags` primary is still
defensible on principle — admin state is what the script wants to know — but it is **hardening, not
the fix**, and the audit section above is wrong to present it as the cause.

**The error shape, for the fourth time in three days and the third time mine:** a correct general
reading (`operstate` *is* an RFC2863 carrier notion) composed into a specific claim about this
device that was never measured, then defended with a fixture built from the claim. A fixture authored
by the same person as the hypothesis tests the hypothesis against itself. The device reads cost one
ssh line and would have settled it before the commit. *Falsified by:* a Pager reporting
`flags` with bit 0 set while `operstate` reads `down` on a monitor vif.
